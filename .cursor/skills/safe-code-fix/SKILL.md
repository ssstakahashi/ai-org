# Safe Code Fix Workflow

コード修正の依頼を受けたら、いきなりファイルを編集せず、以下の4ステップを順に実行する。

## Step 1: 現状調査と影響範囲の特定（読み取り専用）
1. 関連するファイル、型定義、スキーマ（Drizzle / Zod など）、テストコードを特定して読む。
2. 変更で影響を受ける呼び出し元・依存関係（APIエンドポイント、フロントエンドのコンポーネントなど）を洗い出す。
3. エラーログや再現条件があれば、根本原因（Root Cause）を特定する。
4. `git status` で未コミットの変更を確認し、自分以外の変更は混ぜない。

## Step 2: 修正計画（実装前）
変更前に、次の形で簡潔な計画をまとめる。
- **原因・課題**: 何が問題か（1〜2文）
- **変更対象ファイル**: 修正するファイルパスの一覧
- **変更方針**: どの関数・ロジックをどう変えるか
- **破壊的変更・リスク**: 既存機能や型定義、DBへの影響の有無

依頼者が「そのまに進めて」「実装して」と言っている場合、または軽微なタイポや1ファイル内で完結する修正の場合は、計画をまとめたらそのまま Step 3 へ進んでよい。DBスキーマ変更・データ削除・大規模改修・仕様判断が要るものは、実装せず計画を報告して確認を待つ。

## Step 3: 最小限の実装（Minimal Diff）
- 依頼スコープ外の変更（無関係なフォーマット変更、勝手なリファクタリング、コメント削除）はしない。
- 既存のコーディング規約、命名規則、エラーハンドリングのパターンに従う。
- `any` 型チ型アサーェョン（`as`）で型エラーを強引に回避しない。
- 新しいブランチで作業し、意味のあるコミットメッセージを付ける。

## Step 4: 検証と完了報告
1. 型チェック（`tsc --noEmit` / `bun run typecheck` など）、ビルド、リンター、関連テストを実行し、エラーがないことを確認する。今回の差分と無期存の失敗は、その旨を区別して記録する。
2. push・デプロイが許可されていればプロジェクトの通常手順で反映し、本番で反映を確認する。
3. 次の形で完了報告する。
   - **修正内容の要約**
   - **変更したファイルと主な差分**
   - **検証結果**（実行したコマンドと結果）
   - **コミット / デプロイ状況**と、依頼者に確認してほしいこと

## 依頼の受け方（情報が足りないとき）
依頼に次の4要素がそろっているほど精度が上がる。欠けていてコードやログから補えないものだけ確認する。
- **対象**: リポジトリ・ファイル・画面（例: `src/routes/api/records.ts` と関連フック）
- **事象**: 現在の挙動やエラーログ（例: 送信時に `400`、`ZodError: Expected string, received null`）
- **期待値**: ゴールの挙動（例: `date` 未入力ならサーバー側で本日（JST）を補完して保存）
- **制約**: 変えてはいけないもの、通すべき検証（例: APIレスポンスの型は変えない、`bun test` を通す）

依頼テンプレート:
```
@safe-code-fix 以下のコード修正をお願いします。
【対象リポジトリ / ファイル】
【現在の事象 / エラー内容】
【期待する挙動（ゴール）】
【制約・注意点】
```
