## 「全部ほしい」は、いちばん高い入り口

社内ツールの相談でよく出るのが、次のような一文です。

- Excelと紙とチャットに散らばっている業務を、**ひとつのシステムにまとめたい**
- 画面も帳票も権限も、最初から揃えておきたい
- 仕様書を厚くしてから、一括で発注したい

気持ちはわかります。ただ、中小企業の現場では、その入り方がいちばん高くつきやすいです。半年かけて作ったのに、現場が「普段のやり方と違う」と使わない。途中で業務が変わって、仕様変更のたびに見積もりが膨らむ。

前回までの記事では、[アジャイル（育てる開発）が中小企業に合う理由](https://www.studiofoods.net/blog/software-development-agile)と、[AIで開発が早く・安くなった背景](https://www.studiofoods.net/blog/ai-faster-cheaper-dev)を書きました。今回はその次です。**定額で育てる [SODATE](https://www.studiofoods.net/services/sodate) でも、一回限りの受託でも、最初に切る「1本の要件」の切り方**を実務目線で整理します。

## なぜ「全部」が失敗しやすいか

全部を一度に作ろうとすると、だいたい次の3つが起きます。

1. **画面より前に、言葉だけが増える**  
   現場が触っていないうちに、項目名・権限・帳票の議論が膨らみます。触って初めて分かる違和感が、仕様書の段階では出ません。

2. **「使わない機能」まで予算に入る**  
   頭の中の理想を全部盛ると、実際の運用では週1も触らない画面が出ます。あとから「要らなかった」と分かっても、すでに払っています。

3. **変化に弱い**  
   中小企業の業務は、担当者の交代や取引先ルールの変更ですぐ動きます。半年後の完成を前提にすると、完成した頃には前提が変わっています。

だから先に決めるのは「何を全部作るか」ではなく、**何を最初の2〜4週間で動かすか**です。

## 最初に切るのは「機能一覧」ではなく「毎週の流れ」

要件の切り方でいちばん効くのは、機能リストを短くすることではありません。**現場が毎週（または毎日）繰り返している1本の流れ**を切り出すことです。

例です。

| 切り方が弱い | 切り方が強い |
| --- | --- |
| 勤怠・経費・在庫・顧客・帳票を全部 | 「毎週金曜に、現場がExcelへ手入力している出勤実績を、スマホから入れて集計する」 |
| 顧客管理システム一式 | 「見積もり送付後、未返信の案件だけを一覧で追う」 |
| 在庫管理をフル構築 | 「入荷のたびに残数を更新し、発注点を下回ったら担当に知らせる」 |

強い切り方の共通点は、次の3つです。

- **誰が**（役割が1つに絞れる）
- **いつ**（毎日／毎週など、頻度が言える）
- **何が終われば成功か**（入力完了、一覧で追える、通知が飛ぶ、など1行で書ける）

機能は、この流れを支えるための部品です。流れが先、機能は後です。

## 要件を小さく切る4ステップ

スタジオフーズの受託・SODATEで、最初のスコープを決めるときに使っている型です。立派な仕様書は不要です。

### 1. いま一番つらい「手作業の往復」を1つだけ名指しする

「業務全体」ではなく、**週のなかでいちばん時間が溶けている往復**を書きます。

- 紙 → Excel → メール → 再入力
- 担当者ごとの表を、月末に統合する
- 「いまの残数は？」と聞かれるたびに、複数ファイルを開く

ここが曖昧なままだと、画面の話にすぐ逃げます。

### 2. 成功条件を1行にする

「便利になる」では足りません。次のような、観測できる一文にします。

- 金曜17時時点で、出勤実績が未入力の人が一覧で分かる
- 見積もり送付から5営業日超の未返信が、担当別に並ぶ
- 発注点割れの品目が、当日中に担当のチャットへ届く

成功条件が1行なら、最初の試作の範囲も自然に小さくなります。

### 3. 「今回作らないもの」を先に書く

スコープを守るのは、入れる機能より**入れない機能**の宣言です。

例：

- 今回は権限の細分化をしない（管理者／一般の2段階まで）
- 帳票の見た目は後回し（まずはCSV出力）
- 他システム連携はしない（まず手入力またはCSV取込）

「作らない」を先に合意しておくと、定額のSODATEでも、一回限りの受託でも、途中の追加要望を「次の月／次のフェーズ」に回せます。

### 4. 2週間で触れる試作の単位に落とす

切り出した流れが、だいたい次に収まるかを見ます。

- 画面は1〜3枚
- データは主要なマスタ1つ＋実績1つ
- 現場の1人（または少人数）が実データで触れる

収まるなら、それが最初の要件です。収まらないなら、成功条件か「作らないもの」をさらに絞ります。AIで試作が速くなっても、**切り方が大きいと往復コストは戻り**ます。速さは、小さい単位のときほど効きます。

## SODATE（定額）と一回限りの受託、どちらに向くか

同じ「小さく切る」でも、契約の形で向き不向きがあります。

**SODATE（月額定額で育てる）向き**

- 現場のやり方がまだ固まっていない
- 毎月すこしずつ直したい
- 「専任の社内エンジニアがいる感覚」で伴走してほしい
- 優先順位が月ごとに変わりやすい

**一回限りの受託向き**

- 期限と成果物がはっきりしている（公開日、監査、移行日など）
- 切り出した1本の流れが、比較的閉じている
- 完成後しばらくは大きく変えなくてよい

どちらでも、最初の切り方は同じです。違うのは、**切り出したあとを毎月育てるか、区切って納品するか**です。迷ったら、「3ヶ月後も同じ優先順位か？」と聞いてみてください。変わりやすいならSODATE側が合いやすいです。

## 打ち合わせ前に用意しておくもの

仕様書は不要です。次の4点があると、初回の試作までの距離が短くなります。

1. **いま使っているExcel／帳票の実物**（空のテンプレより、実績入りがよい）
2. **一番つらい往復を書いた1段落**（誰が・いつ・何をしているか）
3. **成功条件の1行**
4. **今回作らないもの**の箇条書き（仮でよい）

写真や画面キャプチャでも構いません。「きれいな資料」より、現場の生の材料の方が要件は正確になります。

## まとめ

社内ツールで失敗しやすいのは、技術不足より先に、**最初の要件が大きすぎること**です。全部を一度に欲しがるほど、言葉だけの仕様が増え、使わない機能が予算に入り、変化に弱くなります。

先に切るのは機能一覧ではなく、現場が毎週回している1本の流れです。つらい往復を名指しし、成功条件を1行にし、作らないものを先に書き、2週間で触れる単位まで落とす。その型があれば、[SODATE](https://www.studiofoods.net/services/sodate) の定額でも、一回限りの [受託システム開発](https://www.studiofoods.net/services/software) でも、同じように進められます。

「Excelのこの列だけ、毎週の入力を楽にしたい」という粒度で大丈夫です。まずはその1本から、一緒に切り出しましょう。
