## 読者と成功条件（未検証の運用提案）

**読者**: 倉吉周辺の施設栽培（ビニールハウスでの促成・抑制栽培等）で、日誌や少数のセンサーは回り始めたが、「来週の優先」が口頭のまま残っている中小規模の農家・家族経営。農業DXやスタジオフーズ文脈の読者にも、同じ「記録→決断の空白」を埋める型として読める想定です。

**本稿の位置づけ**: 実在パイロットの「何週回したか／口頭確認が何回減ったか」といった実測は、本稿にはありません。したがって **未検証の運用提案** です。効果を断定せず、現場で数えやすい成功条件と代理指標で「続ける／やめる」を自分で判断できる形にします。

**粗い成功条件（まずこれ）**: 月曜朝（またはヘルパー到着時）に、紙1枚またはスプレッドシート1画面で「来週やる」が誰でも読める状態になっている。これが4週中3週以上続けば、儀式は最低限回っています。

ボードは紙・スプレッドシート・既存の日誌アプリのどれでも回せます。**自社ツールは必須ではありません**。

### 前回の要約（5行）

前回の [倉吉の1農家で始めた農業DX。日誌とセンサーを「毎日使う1本」から育てる](https://www.studiofoods.net/blog/kurayoshi-one-farm-diary-sensor) では、紙と感覚に散らばっていた記録を、日誌と少数のセンサーで「毎日残せる1本」にする話でした。最初の切り方がうまくいっても、次に出やすい詰まりは次のとおりです。

## 口頭優先が残るときの具体エピソード（仮説・例）

以下は倉吉の施設栽培周辺でよく聞くパターンを、**仮説・例**として整理したものです。特定農家の実測値ではなく、自園に当てはめられるチェック用の物語です。

- **例A（家族2名・ハウス数棟）**: 日曜夜に「来週はA棟の温度帯を見直す」と言ったつもりが、月曜朝には本人だけが覚えている。ヘルパー到着時に「昨日の夜温、結局どうする？」と聞かれ、通知画面をスクロールして説明する。
- **例B（通知は来るが行動が人依存）**: 閾値超過の通知は家族全員の端末に届く。ある人は「すぐ見回り」、ある人は「日誌にメモして週末」、ある人は「もう見たはず」——同じ異常でも翌日の作業順が揃わない。
- **例C（週末レビューで止まる）**: 週末に温度ログと日誌を並べ、「数字はある」。しかし「で、来週いちばん先に手をつけるのは？」で会話が止まり、結局その週も口頭の優先に戻る。

本稿の提案は、このギャップを **週次の三欄ボード（運用提案）** で埋める、というものです。因果が証明された処方箋ではなく、試して代理指標で検証する型です。

## 1枚テンプレート（複写用）

紙でもスプレッドシートでも、次の表を1枚にコピーして使えます。**三欄＋上限＋監視条件＋完了定義** を同じ面に載せます。

| 項目 | 記入欄（例） |
| --- | --- |
| **週の日付** | 例: 2026-09-22 週／司会・決定者: （氏名） |
| **来週やる（上限: ___ 本）** | 1. …／担当: …／完了定義: …  2. …  3. … |
| **様子見（監視条件＋期限必須）** | …／条件: あと__夜、同じ帯が続いたら上げる／期限: __/__ |
| **やらない・保留（理由一文）** | …／理由: 今週の枠と前提が足りない、など |
| **安全・品質（枠外・当日対応）** | ボード上限の外。発生時すぐ対応し、翌週に一行残す |
| **閾値見直し（週次必須）** | 通知が多すぎ／少なすぎた指標: … → 変更案: … |
| **粗い成功条件チェック** | □ 月曜朝にこの1枚（または1画面）が貼ってある／共有されている |

家族経営では「やらない」を口にすると摩擦が起きることがあります。司会・決定者を先に一文で共有すると摩擦が減ります（1人でも「自分への儀式」でよい）。対立が続くときは、**その場で決め切らず「様子見に監視条件付きで残す」か、翌週の決定者を交代する**、のどちらかを先にルール化しておくと、儀式が感情の場に化けるのを防げます（これも提案であり、万能の調停手順ではありません）。

### 来週やる欄の上限：出発点の例（仮説）

「上限3本」は施設1〜数ハウス・作物が少ないときの**出発点の例**です。枠の総量は増やしすぎず、規模で調整してください。

| 規模の目安（仮説） | 「来週やる」上限の例 | 統合ルール |
| --- | --- | --- |
| ハウス1〜3・作物少なめ・家族中心 | **最大3本** | 新規1本入ったら同欄から1本を様子見／やらないへ |
| ハウス4〜8・ヘルパーあり | **最大5本**（棟×作業でまとめ） | 同じ棟の作業は1行に統合 |
| 作物・棟がさらに多い／権限が分散 | **最大5〜7本**＋「今日の最優先1件」は日次 | 週次は方針、当日の並びは日次へ |

ポイントは **入れ替えは歓迎し、枠の総量は安易に増やさない** ことです（仮説としての運用指針）。

## 日次・週次・当日対応の使い分け

施設栽培では、台風前・病害の急変・設備トラブルなど、**優先判断の本体が日次・当日**になる局面があります。週次ボードは「平時の順番合わせ」の提案であり、緊急対応を週1に先延ばしするものではありません。

| レイヤー | 目安の時間 | 扱うもの | 扱わ���いもの |
| --- | --- | --- | --- |
| **当日対応（ボード外・枠外）** | 発生時すぐ | 設備異常・急な病害兆候・気象警報・**安全・品質に直結する作業** | 「来週やる」への積み上げだけで済ませること |
| **日次15分（任意）** | 朝または作業後 | 昨日の異常の一行、今日の最優先1件、ヘルパーへの口頭指示の確認 | 全ハウス横断の分析、来週枠の大幅入れ替え |
| **週次30分（本儀式・平時）** | 週末後 or 週明け見回り前 | 三欄への仕分け、上限内の「来週やる」、様子見の監視条件、**閾値見直し**、やらない理由 | 緊急見回りそのもの |

### エスカレーション条件（例）

次のいずれかに当たったら、週次を待たず **ボード外の当日対応** に上げます。**安全・品質に関わるものは上限の枠を食いません**（枠外の例外として再掲）。

1. **安全・設備**: 暖房・灌水・電源など、止まると作物・人に即影響するもの
2. **品質**: 収穫物・出荷基準に直結し、先延ばしすると取り返しがつきにくいもの
3. **気象**: 警報・強風・急降温など、見回りを先延ばしできないもの
4. **病害・虫害の急変**: 様子見の監視条件をすでに超えたもの
5. **権限が必要な決断**: 家族・ヘルパーだけでは動かせず、本人の即断が要るもの

終わったら翌週ボード用に「何が起き、何をしたか」を一行残します。

## 繁忙期ルール（休止と再開）

農繁期に週次30分を死守できない週は必ず来ます。儀式が止まるとボード自体が負債になるため、**休止条件と再開条件を先に書いておく**のが現実的です（運用提案）。

| モード | いつ使うか（例） | やること | やらないこと |
| --- | --- | --- | --- |
| **平時（週次30分）** | 通常週 | 1枚テンプレートを埋める／閾値見直し必須 | 分析ダッシュボードの新設を必須化しない |
| **繁忙期・縮小** | 収穫・定植・天候連続など | **日次1行のみ**（今日の最優先1件＋異常1行）。三欄の本更新は休止可 | 「止めている罪悪感」で無理に30分を入れない |
| **再開** | 繁忙の山が一段落した最初の週末／週明け | 溜まった材料を一度だけ三欄に仕分け、上限内に戻す | 休止中の欠席週を全部さかのぼって完璧に埋めない |

休止中も、**安全・品質の当日対応**と「月曜朝に最優先1行が誰か読める」ことだけは維持できると、再開が楽です。

## センサー通知を「欄の材料」にする／閾値見直しは週次必須

通知そのものをタスク化しすぎると、ボードが通知ログ（ノイズ仕分け工場）になります。切り分けの提案は次です。

1. **通知は材料**: いつ・どのハウス・何の指標・どの閾値か、を一行にする
2. **ボードは決定**: 来週やる／様子見／やらない、のどれかだけを選ぶ
3. **行動は短く**: 来週やるに入れたものだけ、担当と完了定義を書く
4. **閾値見直しは週次の必須タスク**: 「通知が多すぎる／少なすぎる」指標を1つでも洗い、変更案か「今週は据え置き」を書く。閾値が悪いとボードがノイズ工場になるため、任意扱いにしない

完了定義の例:

- 「ハウスBの夜温下限を○℃に変更し、3夜分のログを日誌に貼った」
- 「ヘルパー向けに、週の水やり・葉かきの順番を1枚に更新した」

分析ダッシュボードは、三欄が数週間回ってからで十分なケースが多い、というのが仮説です。複数棟・複数作物の横断比較が経営判断の前提なら、並行してよい、という意味であり、「きれいな画面はあるが来週の順番は口頭」に戻らないための注意です。

### 「様子見」が溜まるトレードオフ

- 様子見には **監視条件と期限** を必ず書く
- 2週連続で条件も期限も無い様子見は、週次で **やらない（理由一文）か来週やるへ強制仕分け**
- 「断りづらいから様子見」は避ける。やらない理由は批判ではなく「今週の枠と前提」の記録

## 効いているかを見る指標（粗い条件＋代理指標）

効果を「収量が○%上がった」と断定するデータは本稿にはありません。代わりに、測定コストの低いものから置きます。

| 指標 | 見るもの | 目安の見方（仮説） |
| --- | --- | --- |
| **粗い成功条件（推奨）** | 月曜朝に紙1枚／1画面で「来週やる」が読めるか | 4週中3週以上なら儀式は回っている |
| 口頭説明の回数 | 「昨日の異常／来週の順番」を口頭だけで説明する回数 | 減っているか（測れるときだけ） |
| 優先の再確認回数 | 「で、今日いちばん先は？」と聞き返す回数 | 月曜朝・ヘルパー到着時に減っているか |
| 様子見の滞留 | 「様子見」に2週以上残っている件数 | 増え続けていないか |
| 閉じた決定の有無 | 週次メモに「やった／持ち越し／やめた」が残っているか | 残せていれば儀式は回っている |

代理指標は測定コストが高い場合、**粗い成功条件だけでも構いません**。物差しであり、ボード万能の証明ではありません。

## 週次30分の進め方（平時の例）

曜日は現場のリズムに合わせます。「週末の作業が一段落したあと」か「週明けの最初の見回り前」が現実的なことが多い、というのが現場ヒアリング上の仮説です。

1. **直近7日の日誌をざっと見る**（未入力があればその場で1行。完璧にしない）
2. **通知・気になった点を材料リストにする**（最大10行。超えたら統合）
3. **三欄に仕分ける**（来週やるは上限厳守）
4. **来週やるだけ完了条件と担当を書く**
5. **閾値見直しを1行書く**（必須）
6. **前週の「来週やる」を閉じる**（できた／持ち越し／やめた）

道具は、前回記事の日誌アプリとセンサー通知、あるいは紙とカレンダーで足ります。新しいBIは必須ではありません。

## SODATEの優先ボードと似ている点／違う点

社内の受託開発でも、[小さく切ったあとに優先ボードで枠を守る](https://www.studiofoods.net/services/sodate) 話があります。農作業の週次ボードとは **型は近いが、失敗コストと時間制約が違う** ので、無批判に同じものだとは言いません。

| | 似ている点 | 違う点 |
| --- | --- | --- |
| **枠の守り方** | 入れ替えは歓迎・総量は増やさない | 開発はスプリント単位、農作業は天候・生育で当日が本体になりうる |
| **材料の扱い** | ログ／通知を「決定の材料」に落とす | 農業は生き物・気象の不可逆が強く、様子見の期限が短い |
| **失敗コスト** | 優先を外すと手戻り・説明コストが増える | 農業は収量・品質・安全に直結しうる。緊急はボード外が前提 |
| **決定者** | 枠の最終決定者を明示すると摩擦が減る | 家族経営では「やらない」表現そのものに配慮が要る |
| **リズム** | 定期の短い儀式で口頭優先を減らす | SODATEは月次寄り、本稿の提案は週次＋日次／当日＋繁忙期モード |

「枠を守る」「材料と決定を分ける」は共通で借りられる型です。上限の数字や週次だけで足りるかは、施設規模と気象リスクで再設計してください。

## 小さく続けるときに決めておくこと

1. **週次の枠**: 何曜日・何分・誰が司会／決定者か
2. **来週やるの上限件数**（上表を出発点に）
3. **様子見の監視条件と期限**
4. **エスカレーション条件**（安全・品質・気象・急変・権限は当日・枠外）
5. **閾値見直しを週次必須にする**
6. **繁忙期の休止／再開条件**
7. **今回やらないこと**（全ハウス横断の自動分析を必須化しない、など）

判断ボードの目的は、会議を増やすことではなく、**迷いや説明の手間を省いて現場作業の時間を守ること（省力化）**にあります。

## 付録：導入率の統計（背景）

本論の根拠ではなく、**導入 ≠ 運用成熟** の背景としてだけ置きます。使うならこの1段落で足り、詳細は参照元へ。

農林水産省の2025年農林業センサス（概数値・令和7年2月1日現在）では、データを活用した農業を行っている農業経営体は33万1千（農業経営体の**40.0%**）。日本政策金融公庫の農業景況調査（令和7年1月・有効回答6,889先）では、スマート農業の導入割合は**44.9%**。一方、導入課題の上位に「初期投資費用が高い」79.0%があり、「データの活用が難しい」17.7%も課題リストの一項目です。センサスは「データを活用しているか」の規模感、公庫調査は導入の広がりを示すものであり、「来週の優先が口頭のまま」の直接証拠ではありません。ボードがこの課題を解く、という接続も著者の推論（仮説）です。
